# M1-4 全链路优化

```bash
source scripts/env.sh
python3 M1/M1-4/camera_pub.py
# 另一终端：
python3 M1/M1-4/image_proc.py
# 一键复跑四组实验，保存每次独立日志：
.venv-ros/bin/python M1/M1-4/measure_chain.py --seconds 24
```

实际平台：Ubuntu 22.04 VMware、6 vCPU。下表来自本机测量，和题目给出的参考数字不同。

|版本|输入（发布者自报）|输出 Hz|控制 Hz|端到端 P95|
|---|---:|---:|---:|---:|
|培训原版|7.36 Hz|1.512|1.512|4780.55 ms|
|两端优化，仍传 BGR|见原日志|18.998|21.000|26.86 ms|
|最终灰度传输|31.997 Hz|31.719|20.993|26.71 ms|

改动：发布端用 NumPy 广播生成与原版相同的 BGR 像素，然后用相同 BGR→灰度规则先转 mono8；发布 640×480，字节数降为原来的三分之一。处理端以查表代替两重逐像素循环，保留原先 1280×720 中间插值、提亮饱和、整数向下取整和最终 640×480 插值。订阅队列为 1；控制与图像节点放入双线程 executor，OpenCV 运算释放 GIL。输出 header 沿用输入，未重打时间戳。

定时器使用 32 Hz 和 21 Hz，给目标 30/20 Hz 留少量运行余量；表中的频率来自实际发布和接收数量，不用定时器设定值冒充实测。输入频率只读发布端自身 `[CAMERA]` 日志，不用订阅者读数替代。

取舍：公开相机话题不再保留彩色，后续若需颜色识别应另开彩色源；低延迟队列在过载时允许丢旧帧；双线程增加一点线程资源。本题本来只要求灰度增强，所以处理语义保留。这里的 30 Hz 是题目合成相机性能，不代表 K230 USB 相机已达到 30 Hz。

单端实验也已实际执行：仅改发布端时输出/控制约 1.276 Hz、P95 1816 ms；仅改处理端时输出约 2.908 Hz、控制 21.001 Hz、P95 19.01 ms，发布端仍为瓶颈。原始记录在 `results/measurements.json`；最终复测在时间戳子目录。故障原文与排查见 FAULTS.md。
