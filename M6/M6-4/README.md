# M6-4：有界推理流水线

```bash
.venv-model/bin/python -m pytest -q M6/M6-4/tests
.venv-model/bin/python M6/M6-4/pipeline.py --model M6/M6-1/models/best_fp32.onnx --source hardware/k230/smartcar_usb_20261116_200340 --threads 3 --seconds 180 --out M6/M6-4/results/triple
```

串行、双线程、三线程共用一个模型和输入源。预分配6个Slot，每个含输入/输出缓冲区；两个Queue上限4，队列传Slot引用，不序列化/复制帧。预处理必要的布局/类型转换与一次copyto明确存在，不把“队列零拷贝”说成全链路绝无拷贝。地址记录能核对同一Slot指针；CPU ORT使用IOBinding直接写入预分配输出。推理只由一个阶段拥有，并有锁保护；没有每帧新建线程。

队列满时阻塞，池空时生产者等待；正常停机停止接收新输入、排空已接收帧再退出。任一阶段异常通过Event通知其它阶段，所有线程join，异常不被吞掉。测试覆盖数据与串行一致、背压、计数守恒、故障退出、停止排空等，共6项。

三方案各跑180秒：串行约30.23FPS，双线程约28.36FPS，三线程约31.40FPS；三线程5659帧，produced=inferred=consumed，内部丢帧0，预热后RSS波动约2.15MB。原始RSS/CPU/延迟CSV全部保留。

**加速比仅约1.04，未达到1.6**。本次CPU模型体占绝大部分时间，轻量预/后处理可重叠部分很小；队列饱和还使三线程端到端P95约253ms，高于串行约46.5ms。不能将较高吞吐等同于更低单帧延迟。文件源未按物理30Hz节流，是吞吐压力测试；它不代表6.25FPS USB相机或Orin板端成绩。

3分钟稳定性和背压工程验证已完成，Orin上的摄像头实时吞吐、GPU缓冲与≥1.6加速比仍需实测/优化。若板端仍由模型体瓶颈限制，应先加速推理，再按队列深度与延迟目标调容量，不能靠丢帧、假睡眠或人为拖慢串行基线提高倍率。
